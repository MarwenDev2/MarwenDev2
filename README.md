**Current problem:** The pipeline uses an SNMP relay to power cycle the DuraCore hardware, which is:
- Slow (approximately 30 seconds per cycle)
- Unreliable (relays can fail)

### 5.2. Current State / Things to Change

- Physical wear on relay components
- One relay already broken due to excessive use

- Fast (approximately 10 seconds per reboot)

## 6. Post-Review Pipeline Stabilization

### 6.1. Purpose of the Technical Review

After the initial functional implementation and the university progress presentation, the Linux workflow was reviewed in detail with the professional supervisor. The review focused on conformity with the established Jenkins pipelines, result traceability, shared-resource protection, and readiness for integration.

### 6.2. Main Findings

| Finding | Required Correction |
|---------|---------------------|
| The Linux Jenkinsfile differed significantly from the reference pipeline | Reuse the canonical stage structure and change only Linux-specific behavior |
| An explicit checkout stage duplicated the pipeline-from-SCM behavior | Remove the unnecessary checkout stage and rely on the job's SCM configuration |
| Established build and test resource locks were missing | Restore the canonical locks to prevent interference with shared environments |
| Delivery, result documentation, publication, and summary stages were incomplete | Restore the full result chain before sending notifications |
| An email could reference result files produced by another pipeline | Generate the summary and notification only from results belonging to the current execution |
| The remote Linux workspace was hardcoded | Pass the current workspace in CI mode and make it configurable in manual mode |
| Temporary debugging logic and changes to shared files remained | Remove debugging artifacts and keep modifications minimal and target-specific |

### 6.3. Corrected Stage Organization

The stabilized pipeline follows the existing pipeline lifecycle:
1. **Checkout**: SCM checkout managed by Jenkins
2. **Build**: Protected build on Linux node
3. **Deliver**: Artifact preparation and archiving
4. **Test**: Protected AIDASS test execution on Windows node
5. **Document Test Results**: Test-result documentation and publication
6. **Summarize Results**: Summary generation
7. **Email Notification**: Current-run email notification

**Key Principle:** The software startup stage is not independent because AIDASS must control the start, stop, and reset lifecycle for each test chapter.

### 6.4. Validation Principle

Every correction is performed incrementally:
1. A small change is introduced
2. Tested
3. Compared with the established Windows and VxWorks behavior
4. Documented
5. Only then retained

This approach reduces merge risk and protects the shared verification infrastructure.

### 6.5. Results

Following the implementation of all corrections:
- Pipeline successfully stabilized
- All stages properly aligned with the reference pipeline structure
- Resource locks in place
- Full result chain preserved from build through delivery, documentation, and email notification
- Email notifications correctly reference only results from the current execution

**Conclusion:** The post-review phase distinguishes a functional prototype from an industrially compatible pipeline extension. It ensures that the Linux implementation preserves established controls, publishes reliable results, and remains maintainable.
